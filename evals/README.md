# 运行行为评测

用这些案例检查 skill 是否帮助用户形成研究提示词，同时避免默认规格问卷。实际调用模型生成回答，再依据语义评审。静态校验不能代替这一过程。

## 准备一次运行

1. 读取 `cases.json`、`plan.json` 和 `rubric.md`，在生成回答前冻结案例、模型、推理强度与通过标准。
2. 为每个案例与模型创建独立工作目录。目录只放 `skills/grill-my-research/` 的副本，以及本案例的 request。使用中性目录名，不包含评测术语。
3. 给每个代理同一案例的完整请求，要求读取副本中的 `SKILL.md`，将给用户的回复保存为 `response.md`。只提供 request，不提供 expected、must_not 或评分规则。使用新会话，不继承本仓库的开发对话。
4. 记录实际模型、推理强度、入口及引用文件的 SHA-256。保留完整响应，并从实际工具记录确认入口读取，不能只接受代理自报。

案例含 follow_up 时，先保存首轮回复，再在同一会话发送该补充内容，记录最终回复。两轮合并供评审。若代理没有按要求保存文件，可以从运行记录中的原始最终回复恢复，不得手写或改写响应，并记录其来源。

每个模型独立完成每个案例。调度器应限制文件访问到该工作目录。生成代理不接触其他输出或评分标准。仅为评测而要求的文件保存不算用户提示词的输出内容。

## 独立评审

1. 所有回答完成后，打乱标签，整理原请求和输出。向评审隐藏模型、代理身份及开发过程。
2. 加入 `rubric.md` 指定的负向对照。用独立代理对全部匿名输出按同一标准评审，保存为 `verdict.json`。
3. 自己逐份阅读输出，核对评审依据与工具记录。若有分歧，记录争议并重新审阅，不能只改判定凑齐通过。
4. 有真实行为失败时先修复 skill，再用新会话重跑受影响案例。保留旧记录。结果所对应的 skill 摘要必须与发布内容一致。

## 保存证据并检查发布条件

每次运行放在独立结果目录。`manifest.json` 记录案例与模型的预定组合、文件摘要和输出映射。每条记录包含匿名 label、case_id、model、effort、output 及实际入口读取证据。负向对照单独记录，不计入通过数。

使用 Python 3.9 或更新版本，在仓库根目录执行：

```sh
python3 scripts/check-evals.py evals/results/2026-11-02
python3 scripts/test-evals.py
```

命令只核验已保存证据的完整性和评审结论，不会调用模型或代替语义评审。缺失组合、重复记录、文件摘要不符、入口读取未确认、行为失败或负向对照漏判都会导致失败。

`test-evals.py` 用临时副本验证门禁：完整证据应通过；删除运行或模型、篡改输出或记录、标记行为失败、漏判对照及未完成复核应被拒绝。它不会改写保存的证据。

重新评测时遵循上述流程并使用新的结果目录。不要把旧输出重新打分后声称重新运行。默认不安装评测材料，它们与可分发的 skill 目录分开。
